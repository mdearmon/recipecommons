# Recipe Commons maintenance instructions

This Site is a public shared recipe catalog with private user collections. Preserve these approved requirements on future edits:

- Store shared recipe content once. Collections, private notes, preferred servings, and folders reference shared recipe IDs.
- Only creators and the configured administrator may edit originals. Customization creates a uniquely named recipe linked to the original revision.
- Ingredients precede steps. Each ingredient use in a step has a numeric allocation in the ingredient's original unit and an ingredient token in the instruction. Render those tokens with quantities for the selected serving count.
- Scale from canonical original quantities for integer servings 1–25. Never accumulate rounding or automatically scale cooking times or temperatures.
- Default to US customary measurements. Preserve originals. Convert mass to volume only for exact ingredient/preparation matches in a referenced density table; mark approximate. Use oz/lb when density is unknown, and never conflate oz with fl oz.
- Import website/YouTube URLs, pasted recipe text/transcripts, PDFs, and JPG/PNG/WebP photos. Extraction is a draft requiring explicit human review. Do not invent ambiguous handwriting, amounts, servings, or ingredient allocations. Missing servings, incomplete ingredients/steps, and conflicting allocations block publication.
- All import and recipe-save routes require sign-in. Screen drafts and published recipes for profanity, slurs, epithets, contextual abuse, and unrelated links on the server; fail closed when unchecked content cannot be screened. Preserve imported provenance via account-bound receipts. Allowed links use attributed source hostnames only; original URL attribution belongs at the bottom, including print layout.
- Complete customized recipes default private and cookable, with collection/folder support. Publication is explicit. Other users cannot see/save/rate private entries. Once a public variation has been saved/rated by someone else, its creator cannot return it to private or delete it; an administrator may remove it.
- Ratings are 1–5 integer stars, one active rating per signed-in account/recipe, editable/removable, require self-reported cooking, and exclude the contributor. Preserve ratings across edits; track revision/fingerprint and show an update notice when cooking details differ. Customizations start with independent ratings and counts.
- Public saved-by counts are distinct current collectors excluding the contributor, not save/remove actions. Highest-rated sorting ranks recipes with at least five active ratings ahead of smaller samples. Administrator rating removal requires a reason and audit event, never impersonation; users may rate again afterward.
- Search by name, included/excluded ingredients, meal, cuisine, cooking method, and pantry matching. Do not infer dietary or allergen guarantees.
- Preserve revision history and show collected-recipe change notices. Contributors cannot delete recipes with active collectors, ratings, or dependent customizations. Administrators can remove any entry using recoverable deletion, preserving references/history and restoring original visibility. Do not allow contributors to republish an admin-removed entry.
- Keep reports and moderation private to ADMIN_EMAIL. Keep private draft, collection, and folder authorization server-side.
- Keep OPENAI_API_KEY only in ignored local env files and native Sites runtime secrets. Never print or commit it. Preserve dispatch-owned ChatGPT authentication and Sites build integration.
- Keep the existing project_id in .openai/hosting.json. Use the Sites skill to synchronize exact source, build/package, and publish. Preserve public audience unless the user changes it.

Verification: run `node node_modules/typescript/bin/tsc --noEmit` and `node --experimental-strip-types --test tests/*.test.mjs`. Build through the Sites plugin helper. For integration tests, apply local D1 migrations, supply the existing API key through an ignored test runtime env file without printing or duplicating it, start the built Worker on loopback with `--var ADMIN_EMAIL:admin@sites.test`, and run `TEST_BASE_URL=http://127.0.0.1:<port> node tests/integration.mjs`. That test sends synthetic identity headers only to the local Worker; never run it against production. Inspect mobile/desktop views through supported browser tools. Fixture recipes are local-only and must not be seeded into production.

Cooking quantities: step uses distinguish `add` from `reference`. Sum only newly added allocations; later cooking/turning/resting/serving references still repeat and scale the original portion amount. Never bypass missing quantities or invent numeric amounts to enable publication. Keep a regression test for 2 lb chicken handled in several later steps.

Import formatting must be automatic. Missing inline ingredient markers alone must never block publication: stepText renders assigned amounts in a per-step ingredient line when not present inline. Keep collective marinade/coating/sauce instructions usable and keep repeated ingredients in separate source groups. Avoid substring/tag checks that confuse olive oil spray with marinade oil, or garlic with garlic powder. Preserve tests/fixtures/spiedini.txt as the user-supplied regression source. Actual missing quantities, unknown ingredient IDs, inconsistent allocations and missing servings must still block publication.
Fresh garlic, garlic powder, and garlic salt are distinct ingredient identities/search tags. Do not substitute or collapse their recipe entries; retain separate quantities for fresh garlic used in multiple source groups.

Text link enforcement must use detected URLs/domains and the source-host allowlist; never let a model's unrelated_links boolean independently veto link-free submitted text. Model visual/full-page screening remains appropriate before extraction, followed by deterministic checks on extracted recipe text. Return the offending hostname for actual text-link rejections. Regression source: tests/fixtures/spiedini.txt must pass with no source hosts.

Approved ingredient tracking (October 13): the first preparation or cooking use allocates an amount once. Later preparation, cooking, moving, and serving refer to the same portion. Track distinct splits and recombination with ingredient IDs, stable portion IDs, and earlier 1-based step links; reject oversized, duplicate or forward references. Ingredient-list evidence grounds shopping quantities; never revise a shopping total merely to fit the steps. Preserve separate groups and fresh garlic versus garlic powder. At most one source-based correction pass; unresolved issues become plain-language questions and remain private drafts. Recheck existing recipes with an accessible original URL or original text/file supplied again; retain no raw imports. Present proposals without saving; creator/admin applies through normal revision/ownership checks. Preserve backwards compatibility for old valid recipes lacking portion fields. Test with tests/ingredient-tracking.test.mjs, tests/portion-import.integration.mjs, tests/recheck-source.integration.mjs, and tests/spiedini.import.mjs. All integration fixtures stay local.

Import transport: browsers request application/x-ndjson progress streaming for long AI imports/rechecks. Send early bytes and five-second heartbeats; carry original errors in terminal records and preserve JSON compatibility for other clients. Do not retry AI submissions automatically. Keep pasted text on connection failures and reject truncated streams as incomplete. Maintain tests/import-transport.test.mjs and the local-only tests/import-stream.integration.mjs. Show the release version in the top-right header and increment it for each published release.
